# Trusted-processing encryption — GDN-026

The component in `services/workers/src/trusted-encryption.mjs` encrypts bounded server-processed restricted material. It is disabled by default, has no mounted endpoint and does not provide a production key manager. No real research record or key has been processed by this implementation. **Authorized application processes and their operators can access plaintext. This is not end-to-end encryption.** Sealed ciphertext is rejected rather than silently downgraded.

## Key and content contract

The trusted host resolves immutable record-version metadata after audited identity and object authorization. Caller-provided classification, purpose or environment is never accepted as truth. `restricted_research`, `sensitive_contributor` and `operational_security` use distinct key references. Public, sealed and governmental classifications are excluded. The configured repository, environment and provider identity must match exactly; preview activation is unsupported. Production bindings and credentials are not committed.

Each encryption uses a fresh random 256-bit content key and 96-bit nonce with Node's AES-256-GCM. The 128-bit authentication tag covers a stable context containing the format, algorithm, workspace, object/version, environment, classification and purpose. Both cipher and decipher explicitly require a 16-byte tag; tags of any other length are rejected before key use. Content is bounded to 8 MiB (a host may lower that limit); this is not a streaming large-archive encryptor. The private envelope stores ciphertext, nonce, tag, opaque wrapped key and exact provider/key versions. It must remain in restricted storage. Metadata is visible to the operator and can itself be sensitive.

Context and envelope serialization use fixed, enumerated field order. A JSON round trip that changes object property order, as PostgreSQL `jsonb` may do, preserves authenticated context and `envelopeDigest`. This is a schema-specific canonical representation, not a general JSON canonicalization standard. Unknown properties, accessors, alternative algorithms and noncanonical base64url encodings are rejected. The digest validates representation but does not itself authorize access or prove persistence.

`createKeyProviderAdapter` requires an operator-configured authenticated client with `wrapDataKey` and `unwrapDataKey`. `createTrustedEncryption` accepts only an adapter created by that factory, so a structural lookalike cannot bypass its reply checks. Client methods and request metadata are captured; the client receives frozen metadata and an owned copy of the key-material buffer. Responses must bind the provider ID, exact key reference/version and context hash to those captured values. An exact raw-key echo is rejected as a wrapper. These checks do not prove that an arbitrary client actually encrypts securely. Root keys are never requested or exported through this contract. The local fixture uses generated root keys solely inside the test process. It is not an HSM, hardware attestation, managed KMS or authorization to use another project's keys.

The [Federal Encryption Compliance README](https://github.com/neophilism/Federal-Encryption-Compliance/blob/main/README.md) was inspected again during recovery (README Git blob `1d5aa6b841900def323e47536ae9b5bfd2f34096`; this identifier is a file blob, not a commit). It describes a compliance-policy application over `@caiae/sdk`; that description supplies no verified key-wrapping contract. It is therefore not adopted as this component's KMS. No upstream implementation was copied. An actual key-service transport, provider IAM, project/environment-specific custody, key attributes, access/rotation policy and recovery configuration must be established before the host connects this component to real data. Shape-valid replies do not establish those facts.

## Authorization, auditing and failure

`createTrustedEncryption` requires `decisions.decide`, `authorize`, `resolveTarget`, `audit`, `keyProvider`, pinned bindings and explicit enablement. `enabled` must synchronously return the boolean `true` from current server state. Missing, false, truthy nonboolean or asynchronous enablement never activates the component. The first audited authorization occurs before metadata lookup. Each audited gate validates the established actor and authoritative record context; after the decision's asynchronous audit tail, it rereads metadata and current permission. The provider attempt audit is followed by a fresh gate before the actual provider call. Enablement and cancellation are checked synchronously after asynchronous authorization/audit work and immediately before key dispatch or returning a result. Durable audit refusal blocks use or delivery. The host must supply record-specific current authorization; mere workspace membership is insufficient.

`authorize(facts, spec)` is a repeatable current-state read, not a one-shot side effect. The key-use spec includes the actual `providerOperation` (`wrap` or `unwrap`), the exact `keyVersion` requested at that operation, and the configured `targetKeyVersion`. Rewrap permission must cover old-version unwrapping and new-version wrapping separately. `resolveTarget` must read authoritative immutable-version metadata rather than caller assertions or stale classification caches. The host must preserve authenticated request identity and enforce its current session, grant and purpose policy.

These sequential callbacks do not create a transactional authorization lease. A grant can change after its last authoritative read, and a caller can persist or transmit a returned buffer later. The host must bind storage commits and downstream delivery to its own current authorization/version transaction, and provide deadlines for identity, permission, metadata and audit dependencies. The component does not implement those transactions, a provider-side authorization policy, HTTP delivery, or a complete request-wide deadline. Audit entries represent the gate or key operation they observed; a `completed` key-use entry does not prove later result delivery or publication.

Key-use events contain only enumerated operational fields and opaque identifiers. They contain no plaintext, raw or wrapped keys, ciphertext, headers, arbitrary provider errors or source titles. Attempt and completed events are distinct; a recorded attempt is not successful decryption. Audit storage itself remains restricted. Failures use one redacted error. Provider calls receive an abort signal and a bounded deadline; there is no plaintext fallback or second provider. API work and actual unsettled provider calls are limited separately, to at most the configured `maxConcurrent` (1–8) per component instance.

A provider that ignores cancellation continues to consume its slot until its promise settles. Repeated caller timeouts cannot create more underlying calls on that instance. An eventual unwrap reply after timeout/cancellation is discarded and its reachable key buffer cleared. A permanently unsettled provider can exhaust capacity; fail-closed replacement of the affected process is then an operator recovery action. The host must enforce any limit shared across multiple instances and processes. Cancellation does not forcibly terminate provider code, network work or native cryptography.

GCM authentication must complete before plaintext leaves the component. Temporary content keys and plaintext copies are cleared on every exit path where held. The wrapping client's owned key copy is also cleared when its signal aborts; an unwrap response still held inside a nonreturning provider cannot be reached by this component until the provider returns it. Both wrap and unwrap reply buffers transfer to the adapter: it copies accepted replies and clears reachable response buffers, including rejected raw-key echoes. Clients must return fresh owned buffers and must not reuse those buffers after settlement. JavaScript garbage collection, native crypto state, provider code and caller-owned copies prevent a guarantee of complete memory erasure; avoid crash dumps, logs and unrelated telemetry in the host. Clients must honor cancellation and must not retain key buffers. The caller owns any successfully returned plaintext buffer and its subsequent lifetime.

## Rewrap, retirement and recovery

Rewrap authenticates the existing ciphertext, unwraps its content key under the allowed old version and wraps it under the configured new write version. It leaves content ciphertext, nonce and tag unchanged. The original envelope is never mutated. A request already on the write version is rejected before key use. The result includes canonical hashes of the complete previous and next envelopes, exact versions and a mandatory compare-and-swap instruction. The host must append the immutable rotation receipt and atomically compare the predecessor hash before changing its active-envelope pointer. This module has no persistence API and makes no claim that a database rotation has committed.

This is **rewrap preparation**, not completed key retirement. Retain the prior envelope and authorized recovery access until all live records, replicas and backup inventories have been reconciled and restored under the new policy. Then separately remove the retired version from allowed reads and enact the provider's verified retirement/revocation procedure. `oldKeyRetirementVerified` always remains false here. Retained envelope rollback is permitted only through authorized incident/recovery procedures and must not undo consent withdrawals or current key-denial policy. No independent rollback anchor is implemented.

Rewrapping does not repair disclosure of a content key or plaintext. A suspected content-key compromise requires a separate fresh-content-key re-encryption/incident workflow. Provider outages or absent old keys make an object unavailable; no new key can recover lost wrapping material. Tests serialize/restore an envelope, reject both an absent and an incorrect restored key, and recover only using the original fixture key. A failed new-version wrap preserves readability of the prior envelope under its permitted old key. This is component recovery evidence, not a full-system backup drill.

## Canonical-standard relationship and activation

The exact pinned E2EESA `ddfbd40c47d13890ebb81ea91c81fe329417058e` documents `spec/secret-storage-hardware-protection.md`, `spec/profile-configuration.md` and `spec/transport-security.md` were read from the canonical repository. Those secret-storage profiles concern device E2EE state; this server-processing format does not claim those profiles, hardware protection, rollback resistance, canonical conformance or certification. Profile selection, transport/IAM and host obligations need their own evidence. The prior standard pin and status record are preserved. Sealed client encryption and recovery remain GDN-027/GDN-028.

Activation needs a real identity/record resolver, current purpose grants, durable private audit service, an authenticated provider with isolated key custody, envelope storage with atomic version binding, and observed provider/restore failures on the deployed source. AI source review and automated tests are required; external expert review remains deferred follow-up under the owner's policy. No new paid resource, public publication or research-route activation is authorized by this component.

Run `node --test tests/security/trusted-encryption.test.mjs` and the existing repository checks. Roll back by disabling/unmounting the host capability while preserving envelopes, audit and rotation history. Never destroy old keys or run destructive schema rollback to reverse application code.

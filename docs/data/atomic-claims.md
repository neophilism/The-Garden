# Atomic claims, evidence evaluations and correction placements (GDN-037)

Status: implementation candidate; research routes remain unmounted. No corpus or personal record was imported. PostgreSQL execution and the exact Node 24 build must pass CI before merge; independent historical/security review and production activation are separate.

A claim has one explicitly structured subject/predicate/object proposition and its original wording. Source testimony, historical interpretation and policy statements are different immutable assertion types. The same record cannot be relabeled from testimony into an accepted historical conclusion. Source testimony requires a durable locator; an unknown named author remains null. Structural atomization is not semantic validation: the batch interface requires explicit researcher segmentation, marks semantic atomicity as needing human review and never splits a paragraph by punctuation or claims that one field necessarily contains one historical fact.

Evidence links name an exact claim revision, a durable locator, a supports/contradicts/contextualizes relation and a rationale. The locator already pins a source revision and byte digest. Conflicting evaluations coexist, and grouping them computes neither a conclusion nor an independent-source count. Links are immutable. A revised claim gets a journal version; existing evaluations continue to refer to the version they actually evaluated.

A placement identifies an artifact kind, identifier, version and optional language. It pins one or more claim, evidence-link or other placement revisions. Web pages, exhibits, translations, charts, books, social graphics, assistant context and downloads are distinct kinds. Identifiers are not fetched or executed. A placement record is not evidence that an artifact is published, rights-cleared or publicly accessible. Placements are immutable; a new artifact placement has a new record identity. The existing append-only revision journal preserves earlier claims.

Correction discovery follows reverse references through source lineage, locators, testimony, evidence and placements. An affected evidence evaluation also schedules re-review of the evaluated claim, allowing changes to a source to reach pages that place its interpretation. These are impact edges, not new historical assertions. Traversal is one PostgreSQL recursive-statement snapshot using UNION deduplication, then current protected-reader authorization of returned records and their dependencies. Record and statement-time bounds fail closed; they never return a silently truncated success. Multiple paths are deduplicated.

Every repository operation uses the existing membership-, purpose- and record-grant-bound executor. Pinned revision reads still require a currently readable envelope. Locator reads authorize the underlying original witness and archival ancestors. Hidden sources cause indirect reads to fail. The correction report explicitly describes only the authorized-record closure; global completeness is not established, and absent private placements are not disclosed. A public release compiler with appropriate scope and a durable correction queue remains later work. No claim is automatically edited, withdrawn or republished by this module.

Migration 0008 adds independent PostgreSQL shape/type/pinned-reference guards, immutable evidence and placement guards, a reverse-dependency GIN index and security-invoker views. Previous migration bytes are unchanged. The generic database role is for trusted repository code only; a raw SQL connection is not exposed to users. Views inherit envelope RLS; application traversal additionally authorizes linked evidence rather than treating a record grant as a grant to every source it names.

## Verification and rollout

Run `node --test tests/data/*.test.mjs` and the existing full checks. The historical-data workflow applies all checksum-locked migrations twice, then runs `apps/research/data/claims.ci.mjs` against ephemeral PostgreSQL. It tests conflicting evidence, immutable links, pinned older versions, concurrent stale writes, direct and transitive correction coverage, source revocation, hidden placement non-disclosure and bounded failure. The CI file refuses managed/non-loopback databases.

Do not apply this migration to the owner's production branch or enable research routes as part of this PR. Before activation, obtain the remaining consent/publication/audit controls, scoped operator credentials, release-wide correction processing, performance measurements on the actual corpus and independent review. Roll back application exposure by keeping routes disabled; retain the additive schema and prior claim history rather than replaying destructive historical migrations.
